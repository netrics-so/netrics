# Custom API builder (milestone 13, plan B) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A workspace member builds a custom JSON API definition in a six-step guided editor, tests it live against a draft connection whose secrets never leave the server, saves it and gets the first connection; afterwards they see the version history, roll back, export and import the definition, and are offered a definition update on each connection.

**Architecture:** A draft connection (`connections.status = 'draft'`, connector `custom-api`) holds the builder's credentials and variable values, bound to the hosts they were entered for; it is never scheduled, invisible to every existing connection path, and pruned after 24 h untouched. A test-request endpoint runs one stream of the in-progress definition through a bounded multi-page runner built from C-G3's request, pagination and mapping functions and returns a bounded, value-redacted response tree, mapped preview rows, type suggestions and a request log. The web builder is a pure state model (definition document ↔ step state) rendered as six Signal steps with a JSON tree picker. Versions, rollback, connection updates (pattern of #615: offered, reviewed, applied with a stale-basis check), export and import sit on the C-G2 definition tables.

**Tech Stack:** TypeScript, Fastify, drizzle-orm + PostgreSQL (RLS), zod contracts + generated OpenAPI, Next.js web app (Signal admin components and CSS), vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-20-custom-api-connector-design.md` (sections 3, 5, 6, 7, 10, 11 and the anti-goals). Cross-plan names: `docs/superpowers/plans/2026-11-20-m13-overview.md`.

## Global Constraints

- Connector id `custom-api`; definition schema, `customApiDefinitionSchema`, `CustomApiDefinition`, `CUSTOM_API_SCHEMA_VERSION = 1`, `upgradeCustomApiDefinition`, `CUSTOM_API_LIMITS` come from `packages/connector-sdk/src/custom-api/definition.ts` (C-G1). This plan never redefines them.
- Draft connections: `connections.status = 'draft'`; never scheduled; deleted by a job after 24 h untouched; no pin (version and environment columns null); the unsaved definition in `connections.config.draft`; read by B-G1's `loadConnectionCustomApiDefinition`, which C-G4's OAuth flow also uses (overview contract).
- Test requests: at most 10 open drafts per workspace, one running test per draft, and at most **30 test requests per workspace per minute** (429 `custom_api_test_rate_limited` with `Retry-After` in seconds), counted in the database so it holds across API replicas.
- A credential never appears in a preview, request log, error, export, dataset or API response (spec anti-goal). Redaction is by value (every credential string and secret variable value, raw and URL-encoded) on every string the test endpoint returns.
- Credentials are only sent to the hosts they were entered for: the draft's environment host and declared auth endpoint hosts. Any change of those hosts invalidates stored credentials (spec 3, 5).
- Unmapped data is never stored: the test response is returned, never persisted or logged.
- Test-request bounds (`CUSTOM_API_TEST_LIMITS`): 5 pages, 1,000 records, 60 s total, preview body 256 KiB serialized, 50 array items per array, 2,000 characters per string, depth 32, 100 preview rows (`DATASET_LIMITS.previewRows`). Per-request egress bounds are the F-G2 / spec defaults (10 MiB response, 50 MiB decompressed, 30 s).
- Paths in the UI are the dotted syntax with indexes (`data`, `meta.next`, `items[0].url`); the builder fills them by clicking, never asks for JSONPath.
- Capabilities: create a draft, test, save a new definition, promote: `connections:create`. Edit an existing definition, restore a version, apply a connection update: `connections:update`. Read definitions, history, export: `connections:view`. Import: `connections:create`.
- Tenant isolation twice: RLS on `connections` already applies to drafts; every new query carries an explicit `workspace_id` predicate.
- Every UI string in English and German (informal "du") in `apps/web/src/messages/custom-api/{en,de}.ts` (new area `customApi`), `apps/web/src/messages/sources/{en,de}.ts`, and every new error code in `apps/web/src/messages/api-errors/{en,de}.ts`.
- No private details of the owner's first-party service in code, fixtures or tests; fixtures use `api.example.test` names and the C-G3 fixture server.
- Definition of done (`CLAUDE.md`), per group: `pnpm format:check && pnpm lint && pnpm typecheck && pnpm test`; `pnpm openapi:check` after route/contract changes (`pnpm openapi` regenerates); migrations via `pnpm db:generate`, hand-edited, tried on data in the previous shape; `pnpm e2e` when a UI flow changes; one issue per PR with `Closes #N`; squash-merge on green CI.
- Test command: `NETRICS_TEST_ADMIN_URL=postgres://netrics:netrics@localhost:5433/postgres pnpm vitest run <file>` (root `vitest`; `pnpm db:up` starts Postgres on 5433). Below abbreviated as `pnpm vitest run <file>` with that variable set.

## Review Focus

1. **The builder changes the base URL (or picks another environment, or another token URL) after the secret was entered.** Expected: the test request is refused with `custom_api_credentials_host_changed` before any network call, and the Login step asks for the secret again; the old secret is never sent to the new host. Test in Task 2 and Task 5.
2. **The API echoes the credential back** (a `/whoami` body containing the token, an error page quoting the URL with the API key query parameter, a `Location` with the key). Expected: every occurrence in body, log URL and error text reads `[redacted]`, also URL-encoded forms. Test in Task 4 and Task 5.
3. **A huge or hostile response** (100,000-item root array, 40-level nesting, a 5 MB string, a body that is a bare string or number). Expected: the response is bounded to 256 KiB with `truncated: true`, the tree still renders, suggestions come from at most the first 100 records, and a non-object body gives `custom_api_records_not_array` with the found type, not a crash. Test in Task 3 and Task 4.
4. **Mixed or empty values in the first records** (`null` in some rows, `"12.50"` strings next to numbers, an empty first page). Expected: the field is suggested nullable, mixed numeric strings and numbers suggest `decimal`, mixed unrelated types fall back to `string`, an empty page suggests nothing and says "The request returned no records". Test in Task 3.
5. **The cleanup job runs while the draft is being promoted, or after it was promoted.** Expected: the job only deletes rows still `status = 'draft'` and untouched for 24 h in the same statement; a promoted connection is never deleted; a test request on a pruned draft answers 404 `custom_api_draft_not_found` and the builder offers to start the login again. Test in Task 1 and Task 2.
6. **A pruned or deleted draft holds an OAuth grant.** Expected: the cleanup
   job and the draft delete route revoke it first through C-G4's revoke-on-
   delete path (best effort, failures logged without secrets), then delete the
   row. Test in C-G4's revoke task once both are on main (whichever group
   merges second adds the test).
